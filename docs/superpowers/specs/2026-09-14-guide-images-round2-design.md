# 가이드 글 이미지 추가 2차 배치(5개) 설계 문서

- 작성일: 2026-09-14
- 상태: 승인됨 (구현 계획 단계로 진행)

## 배경 및 목표

1차 배치(2026-09-14, 커밋 `32c5374`~`b18a302`)가 완료·배포되어 `master`/`origin/main`에 반영됐다. 목표는 동일: 텍스트만 있던 가이드 글에 실제 이미지를 추가해 AdSense 재심사 약점("이미지 0개") 대응. 이번 라운드는 2차 콘텐츠 배치(2026-09-13)에 대응하는 5개 글을 다룬다.

1차 배치 최종 리뷰(opus)가 남긴 개선 권고를 이번 라운드에 반영한다:
1. **`<img>`에 `width`/`height`/`loading="lazy"`/`decoding="async"` 추가** — 1차엔 없어서 로드 전 레이아웃 이동(CLS) 여지가 있었음.
2. **인라인 SVG 색상은 하드코딩 hex 대신 `var(--color-*)` 사용** — 1차는 설계 문서와 다르게 hex를 그대로 씀. 최신 브라우저(Chrome/Firefox/Edge/Safari 최신 버전)는 SVG 프레젠테이션 속성에서 `var()`를 지원하므로 안전하게 적용 가능.
3. **차트 수치 테스트를 더 엄격하게** — 1차는 본문에 이미 있는 짧은 문자열(예: `25MB`)만 검사해서 차트를 통째로 지워도 통과하는 테스트가 있었음. 이번엔 `<desc>` 전체 문장처럼 차트에만 있는 고유한 문자열을 검사한다.
4. **SVG 텍스트 라벨의 `text-anchor`를 항상 명시** — 1차에서 `text-anchor` 누락으로 라벨이 viewBox 밖으로 잘려나간 사고가 있었음. 오른쪽 정렬이 필요한 라벨은 반드시 `text-anchor="end"`와 여유 마진을 함께 지정한다.

기존 글 5개에 이미지를 추가한다 (신규 페이지 없음):

## 이미지별 상세 설계

### 1. `web-image-loading-speed.html` — LCP 기준 세그먼트 차트

**사실 확인(이미 본문에 있음, 재확인 불필요)**: 구글 Core Web Vitals 기준 — 2.5초 이하 양호, 2.5~4.0초 개선 필요, 4.0초 초과 나쁨(`web-image-loading-speed.html:38`).

**차트 형태**: 막대그래프가 아니라 가로로 긴 3구간 세그먼트 바(신호등 형태) — 연속된 시간 축 위에 3개 구간을 색으로 구분하고 경계에 "2.5초"/"4.0초" 라벨을 붙인다. 색상은 구글 PageSpeed Insights/Lighthouse가 실제로 쓰는 신호등 색(초록/주황/빨강)을 그대로 채택한다 — 이 사이트의 민트 단색 팔레트를 벗어나는 유일한 예외지만, 업계 표준 관례를 따르는 것이 가독성과 신뢰도 면에서 더 낫다고 판단.

### 2. `cloud-storage-photo-tips.html` — 클라우드 용량 막대차트

**사실 확인(이미 본문에 있음)**: 구글 드라이브 15GB, 아이클라우드 5GB, 원드라이브 5GB, 네이버 마이박스 30GB(`cloud-storage-photo-tips.html:38-41`).

**차트 형태**: 1차 배치의 이메일 차트와 동일한 스타일(막대 4개, `var(--color-accent)` 채움, 값 라벨 상단, 서비스명 하단). 최대값 30GB 기준으로 비례.

### 3. `pdf-file-size-reduction.html` — 실제 "PDF → 이미지" 추출 결과 화면

**캡처 방법**: 1차 배치와 달리 이번엔 이 사이트의 도구 두 개를 실제로 연달아 실행해서 캡처한다.
1. `pdf.html`의 "이미지 → PDF" 섹션에 서로 다른 색의 합성 이미지 정확히 2장을 업로드하고 "PDF로 변환" 클릭 → 생성된 2페이지 PDF를 다운로드 링크(blob URL)에서 직접 가져온다(다운로드 클릭 없이, 1차 배치의 실측 벤치마크 때 확립한 "blob URL fetch" 패턴 재사용).
2. 그 PDF 파일을 같은 페이지의 "PDF → 이미지" 섹션에 업로드해서 실제로 추출을 실행한다.
3. 추출된 페이지 썸네일이 표시된 `#pdfToImgPages` 영역을 스크린샷한다.

이렇게 하면 `pdf-file-size-reduction.html` 본문이 설명하는 우회법의 1단계("PDF를 페이지별 이미지로 추출")를 실제로 수행한 진짜 결과 화면을 보여줄 수 있다 — 손그림 흐름도 대신, 이 사이트가 실제로 하는 일을 그대로 캡처하는 원칙을 지킨다.

### 4. `sns-blog-image-size.html` — 리사이즈 입력 화면 (1080×1080)

1차 배치의 `photo-id-resize.html` 스크린샷(413×531)과 동일한 방식으로, `index.html`의 가로/세로 입력란에 1080×1080을 입력하고 '비율 유지'를 끈 화면을 캡처한다. 인스타그램 정사각형 규격(본문에 이미 있는 값)을 대표로 선택 — 인스타 3종·네이버 2종 규격 중 가장 단순하고 널리 알려진 값이라 대표성이 있다.

### 5. `favicon-og-image-size.html` — 3단 비율 비교 다이어그램

**정직성 문제와 해결책**: 16px부터 512px까지 32배 차이가 나서 전부 하나의 스케일로 그리면 16px가 사실상 안 보인다. 그렇다고 스케일을 속이면(예: 16px를 실제보다 크게 그리면) 비율 왜곡이 된다. 해결책은 **그룹별로 별도 스케일을 쓰되, 같은 그룹 안에서는 정확한 비율을 유지**하는 것 — 인포그래픽에서 흔히 쓰는 방식이다.

- **패널 1: 파비콘** — 16×16, 32×32, 48×48을 2배 스케일(32/64/96px로 표시)로 나란히, 바닥선 정렬.
- **패널 2: 앱 아이콘** — 180×180, 192×192, 512×512를 약 0.3배 스케일(54/58/154px 표시)로 나란히, 바닥선 정렬.
- **패널 3: OG 이미지** — 1200×630(1.91:1)을 약 0.15배 스케일(180×94.5px 표시)로 단독 표시.

각 도형 위/옆에 정확한 실제 픽셀 값을 텍스트로 표기해서, 시각적 비율은 그룹 내에서만 정확하고 정확한 수치는 텍스트로 항상 확인 가능하게 한다(과장이나 왜곡 없음).

## 공통 사항

- 모든 `<img>`: `width`/`height`/`loading="lazy"`/`decoding="async"` 속성 추가(1차 배치 권고 반영). width/height 값은 실제 캡처된 스크린샷의 픽셀 크기를 그대로 쓴다.
- 모든 인라인 SVG: 색상은 `fill="var(--color-accent)"` 등으로 CSS 변수 참조(1차 배치 권고 반영, hex 하드코딩 금지).
- 텍스트 라벨이 있는 SVG 도형은 전부 `text-anchor`를 명시하고, viewBox 경계에서 최소 4px 이상 여유를 둔다(1차 배치 사고 재발 방지).
- 삽입 위치는 1차 배치와 동일한 원칙: 관련 설명 문단 바로 다음, `<section class="info-section">` 안, `.guide-image` figure로 감쌈.
- `image-toolbox`는 git 명령 직접 실행 가능한 예외 저장소. 커밋 attribution은 반드시 `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`.

## 이미지 캡처 순서 (오케스트레이터 전용, 1차와 동일한 제약)

Playwright MCP를 이용한 실제 배포 사이트 조작이 필요한 유형 A 이미지 2장(pdf 추출 결과, sns 리사이즈 화면)은 **오케스트레이터가 SDD 착수 전에 직접** 캡처한다 — 헤드리스 서브에이전트는 브라우저 도구에 접근하지 못할 가능성이 높다는 1차 배치의 결론을 그대로 따른다. 유형 B(인라인 SVG)는 코드로 직접 작성하므로 캡처 불필요.
