## 배경 및 목표

AdSense 재신청 전 점검(2026-09-15)에서 발견한 잔여 리스크 대응. 가이드 글 16개는 전부 각각 본문이 약 1,100~2,000자(FAQ 3개 포함)로 얇은 편이고, 루트 도메인(`nwb010118.github.io`) 첫 페이지는 링크 하나뿐인 스텁 페이지다. 애드센스 반려 사유 중 "텍스트 콘텐츠 절대량 부족"이 페이지 수(8→27)로는 크게 개선됐지만, 개별 글의 깊이는 그대로라 재반려 시 같은 사유가 또 나올 위험이 있다.

목표: 가이드 글 16개를 각각 2,500~3,500자로, 루트 페이지를 스텁에서 실제 소개 콘텐츠로 보강한다.

## 범위

1. 기존 가이드 글 16개(아래 표) — 신규 페이지 생성 없음, 기존 페이지 본문 보강만.
2. `nwb010118.github.io/index.html` — 별도 저장소(`C:\Users\A\projects\nwb010118.github.io`), 별도 git remote.

## 목표가 아닌 것 (Out of Scope)

- 신규 가이드 글 추가(4차 배치) — 이번 라운드는 기존 16개의 깊이 보강만.
- 색인/사이트맵 문제 — 이미 별도로 처리 중(3일 뒤 재확인 예정).
- GA4·백링크·홍보 — 사용자가 보류 확정.

## 보강 방식 (공통 원칙)

글마다 두 가지를 함께 한다:
1. **FAQ 3~4개 추가** (기존 3개 → 6~7개). FAQ 1개당 약 100~150자라 이것만으로는 +500~700자가 한계.
2. **기존 본문 섹션 중 1개를 더 구체적으로 보강** — 새 섹션을 만들지 않고, 이미 있는 단락에 예외 상황·비교·구체적 절차를 추가해 +500~800자를 채운다.

**사실 확인 원칙(기존 프로젝트 규칙 그대로)**: 새로 추가하는 모든 사실 주장(수치, 서비스 정책, 규격)은 WebSearch로 재확인한다. 자사 도구 기능을 언급할 때는 반드시 해당 `js/*.js`를 먼저 확인한다.

**정직성 주의사항(이번 라운드에서 특히 중요)**: `pdf-file-size-reduction.html`과 `pdf-merge-multiple-files.html`에 새로 추가하는 FAQ 중 "재합친 PDF도 텍스트 검색이 되나요?" 류의 질문에는 **반드시 "안 된다"고 정직하게 답한다** — 두 글의 우회 방법 모두 PDF 페이지를 이미지로 추출한 뒤 `photos-to-pdf.html`(이미지→PDF)로 재조립하는 방식이라, 결과물은 텍스트 레이어가 없는 이미지 기반 PDF가 된다. 이 사실을 숨기면 이 프로젝트의 핵심 원칙(자사 도구 기능 오서술 금지)을 어기는 것이 된다.

**중복 방지**: 새 FAQ·보강 문단이 같은 글의 기존 문장, 그리고 다른 15개 글의 기존 문장과 겹치지 않는지 작성 단계에서 대조한다. 최종 전체 브랜치 리뷰에서 문장 단위 유사도를 재확인한다.

**중복 방지(중요)**: 같은 애드센스 계정 아래 `about.html`(image-toolbox 소개 페이지)이 이미 있으므로, 이 루트 페이지는 다른 각도로 쓴다.

## 성공 기준

- 16개 글이 각각 2,500~3,500자 범위에 도달한다.
- 모든 신규 FAQ·보강 문단의 사실 주장이 WebSearch로 재확인됐다.
- `pdf-file-size-reduction.html`/`pdf-merge-multiple-files.html`이 재합친 PDF의 텍스트 비검색성을 정직하게 고지한다.
- 어떤 글도 자사 도구에 없는 기능을 있는 것처럼 서술하지 않는다.
- 어떤 신규 콘텐츠도 같은 글·다른 15개 글·루트 페이지·`about.html`과 문장 단위로 준중복되지 않는다.
- 모든 글의 `FAQPage` JSON-LD 항목 수가 화면 `<details>` 개수와 일치한다.
- 루트 페이지가 실제 소개 콘텐츠를 갖추고 `about.html`과 겹치지 않는다.
- 기존 175개 테스트 + 신규 테스트 전부 통과, 기존 페이지/기능 회귀 없음.
