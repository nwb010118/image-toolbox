# 기존 도구 페이지 콘텐츠 보강 설계 문서

- 작성일: 2026-09-09
- 상태: 승인됨 (구현 계획 단계로 진행)

## 배경 및 목표

AdSense 반려 대응 5단계 계획(1단계 About/문의 페이지는 완료·배포됨)의 2단계. 외부 진단의 핵심 지적 중 "텍스트 콘텐츠 절대량 부족"은 신규 페이지 추가만으로는 완전히 해소되지 않는다 — 사이트의 얼굴이자 가장 많이 방문될 3개 핵심 도구 페이지(`index.html`, `pdf.html`, `upscale.html`) 자체가 여전히 "h1 + 한 줄 부제 + 도구 UI + FAQ 아코디언" 구조로, 실제 설명 텍스트가 거의 없다.

실제 파일을 확인한 결과 진단이 정확했다: 세 페이지 모두 부제 한 문장을 제외하면 원리·사용법·비교 설명이 전혀 없고, 유일한 텍스트 콘텐츠는 FAQ 답변뿐이다.

## 범위

`index.html`, `upscale.html`, `pdf.html` 3개 파일을 수정한다(신규 파일 없음). 각 페이지의 도구 UI(업로드/설정/미리보기 영역) 다음, 기존 FAQ 섹션 앞에 `info-section` 블록을 새로 추가한다.

- `index.html`: 2개 섹션 — "압축은 어떻게 동작하나요", "어떤 형식을 골라야 할까요"
- `upscale.html`: 2개 섹션 — "AI 업스케일링은 어떻게 동작하나요", "언제 필요한가요"
- `pdf.html`: 1개 섹션(짧게) — "이 도구로 무엇을 할 수 있나요" + 기존 3개 롱테일 페이지(`photos-to-pdf.html`/`pdf-to-word.html`/`pdf-to-ppt.html`)로의 링크

콘텐츠는 실제 코드 동작(`js/imageTools.js`, `js/app.js`, `js/upscaleTools.js`, `upscale.html`에서 로드하는 CDN 라이브러리)을 확인해 사실에 기반해 작성한다 — 막연한 마케팅 문구가 아니라 검증 가능한 설명.

## 목표가 아닌 것 (Out of Scope)

- `pdf.html`에 롱테일 페이지들과 중복되는 상세 설명을 넣는 것 — 이미 `photos-to-pdf.html`/`pdf-to-word.html`/`pdf-to-ppt.html`이 각 기능을 자세히 다루고 있어 짧은 개요 + 링크로 충분하다고 판단.
- 새 CSS 클래스, 새 JS 로직 — 순수 설명 텍스트 추가이며 기존 `info-section` 클래스를 재사용한다.
- 기존 FAQ 섹션의 질문/답변 수정 — 새 섹션은 FAQ와 겹치지 않는 내용(원리·비교)에 집중하고, FAQ는 그대로 둔다.
- 3단계(실측 비교 데이터)와 4단계(정보성 가이드 글)는 이 작업 범위 밖 — 각각 별도 라운드로 진행.

## 페이지별 콘텐츠 구조

### `index.html`

1. **압축은 어떻게 동작하나요** — 브라우저의 Canvas API로 이미지를 다시 인코딩하는 방식임을 설명. 실제 코드(`js/app.js`의 `canvas.toBlob(callback, mimeType, quality)`)를 근거로, **JPG·WebP는 손실 압축이라 품질 슬라이더가 실제로 용량을 줄이지만, PNG는 무손실 형식이라 품질 슬라이더가 파일 크기에 영향을 주지 않는다**는 사실을 정직하게 명시한다(브라우저 Canvas API 표준 동작). PNG 용량을 줄이고 싶다면 출력 형식을 JPG나 WebP로 바꾸거나, 가로세로 크기(해상도) 자체를 줄이라는 실전 팁을 덧붙인다.
2. **어떤 형식을 골라야 할까요** — JPG(사진, 압축률 좋음, 투명 배경 불가), PNG(무손실, 투명 배경 지원, 그래픽/스크린샷에 적합), WebP(JPG보다 작은 용량에 비슷한 화질, 최신 브라우저 대부분 지원) 세 형식을 언제 선택하면 좋은지 비교한다.

### `upscale.html`

1. **AI 업스케일링은 어떻게 동작하나요** — 실제 사용 중인 라이브러리(UpscalerJS + ESRGAN 계열 경량 모델, TensorFlow.js 기반으로 브라우저 안에서 직접 실행)를 근거로, 단순히 픽셀을 늘려서 채우는 보간(리사이즈) 방식과 달리 AI 모델이 주변 픽셀 패턴을 학습한 결과를 바탕으로 디테일을 추론해 확대한다는 점을 설명한다. `js/upscaleTools.js`의 실제 동작(모델이 한 번에 2배씩만 확대 가능해 최대 2회 체이닝=4배, 해상도 프리셋은 긴 변 기준으로 목표를 잡고 초과분은 캔버스로 정밀 축소)도 반영한다.
2. **언제 필요한가요** — 오래된 사진이나 작게 찍힌 사진을 인쇄·확대해야 할 때, 저해상도 이미지를 큰 화면(배경화면 등)에 써야 할 때처럼 실제 사용 시나리오를 제시한다.

### `pdf.html`

1. **이 도구로 무엇을 할 수 있나요** — 이미지→PDF, PDF→이미지, PDF→Office 문서(PPT/Word/Excel) 세 기능을 한두 문장씩 짧게 요약하고, 각각 자세한 사용법이 필요하면 해당 롱테일 페이지(`photos-to-pdf.html`, `pdf-to-word.html`, `pdf-to-ppt.html`)로 이동할 수 있는 링크를 건다.

## SEO 영향

기존 페이지의 `SoftwareApplication`/`FAQPage` JSON-LD는 그대로 둔다 — 새 섹션은 스키마 없는 순수 설명 텍스트다(별도 구조화 데이터 타입을 추가할 필요는 없다고 판단). `meta description`/`title` 등 기존 메타데이터도 변경하지 않는다 — 이 작업은 페이지 내 텍스트 분량과 정보 밀도를 늘리는 것이 목적이다.

## 에러 처리

해당 없음 — 순수 정적 콘텐츠 추가로, 실패할 수 있는 로직이 없다.

## 테스트 방침

- 기존 `tests/seoPagesIntegrity.test.js`(Node, 무프레임워크)에 검증 항목을 추가한다: 각 페이지에 새 섹션의 제목(h2)이 존재하는지, `pdf.html`의 새 섹션이 3개 롱테일 페이지 전부로 링크하는지.
- 브라우저로 직접 열어 새 섹션이 도구 UI와 FAQ 사이에 올바르게 배치됐는지, 기존 기능(압축/변환/업스케일링 실제 처리)에 회귀가 없는지 수동 확인한다.

## 성공 기준

- `index.html`/`upscale.html`이 각각 2개, `pdf.html`이 1개의 새 설명 섹션을 갖추고 배포되어 있다.
- 모든 새 콘텐츠는 실제 코드 동작에 근거한 사실이다(검증 없이 작성된 마케팅 문구가 없다).
- `pdf.html`의 새 섹션에서 3개 롱테일 페이지로의 링크가 정상 동작한다.
- 기존 FAQ, JSON-LD, 도구 기능에 회귀가 없다 — JS를 건드리지 않았으므로 자동으로 만족된다.
