# 롱테일 키워드 신규 랜딩 페이지 설계 문서

- 작성일: 2026-08-24
- 상태: 승인됨 (구현 계획 단계로 진행)

## 배경 및 목표

사용자가 SNS 홍보(스레드/인스타/블로그 게시)를 직접 하기 번거로워하며, 계정 접근 없이 자동으로 진행 가능한 유입 채널을 요청했다. 현재 사이트는 `index.html`(압축+형식변환), `pdf.html`(이미지→PDF·PDF→이미지·PDF→문서변환 3기능), `upscale.html`(업스케일링) 세 페이지로 구성되어 있고, 각각 SEO 메타/FAQPage 스키마는 갖췄지만 한 페이지에 여러 기능이 묶여 있어 검색 의도가 좁은 쿼리(예: "PDF 워드 변환")에 대해 관련성 신호가 희석된다.

목표는 검색량이 큰 단일 의도 키워드마다 전용 랜딩 페이지를 만들어 진입점을 늘리는 것. 새 변환 기능을 만드는 게 아니라, 기존 `pdf.html`의 해당 섹션으로 연결되는 "상세 설명 + 딥링크" 페이지를 추가한다.

## 범위

이번 1차로 검색량이 가장 클 것으로 예상되는 3개 페이지를 저장소 루트에 신규 추가한다 (기존 파일들과 동일하게 빌드 도구 없는 순수 정적 HTML, 하위 디렉터리 없이 루트에 위치):

1. `pdf-to-word.html` — "PDF를 워드로 변환" → `pdf.html#pdfConvertUploadArea`로 딥링크 (해당 섹션의 라디오 버튼은 기본값이 PPT이므로, 사용자가 직접 Word를 선택해야 함 — 자동 선택 로직은 이번 범위에 넣지 않음)
2. `pdf-to-ppt.html` — "PDF를 파워포인트로 변환" → `pdf.html#pdfConvertUploadArea`로 딥링크 (라디오 기본값이 PPT라 별도 조작 불필요)
3. `photos-to-pdf.html` — "여러 장 사진 PDF로 합치기" → `pdf.html#imgToPdfUploadArea`로 딥링크

나머지 후보(PDF→Excel, PNG/JPG/WebP 형식 변환, 사진 용량 줄이기, 화질 개선)는 이번 3개의 효과를 확인한 뒤 다음 라운드에서 추가 여부를 결정한다.

## 목표가 아닌 것 (Out of Scope)

- 새로운 변환 기능/JS 로직 — 전부 기존 `pdf.html`의 기능을 그대로 사용한다.
- 딥링크 시 라디오 버튼(PPT/Word/Excel) 자동 선택 — 앵커 스크롤까지만 처리하고, 형식 선택은 사용자가 직접 한다.
- SNS 게시, 백링크 아웃리치 등 계정 접근이 필요한 홍보 활동 — 별도 트랙.

## 페이지 콘텐츠 구조 (3페이지 공통 템플릿)

각 페이지는 얕은 키워드 페이지가 되지 않도록 아래 구성을 갖춘다 (페이지당 한국어 약 500~700자 분량의 본문):

1. **H1 + 상황 설명** — 왜 이 변환이 필요한지 구체적 시나리오 제시
2. **사용 방법 3단계** — 실제 UI 흐름(파일 선택 → 형식 선택/확인 → 다운로드)을 그대로 서술
3. **정직한 한계 고지** — 예: PDF→Word/PPT는 텍스트 레이어가 있는 PDF만 지원하며 스캔본(이미지 PDF)은 지원하지 않음, PDF→Word는 서식 없이 문단 텍스트만 추출됨 등, 실제 기능 한계를 숨기지 않고 명시. 이는 신뢰도를 높이는 동시에 각 페이지가 서로 다른 내용을 갖게 해 유사 콘텐츠 문제를 피한다.
4. **도구로 이동하는 버튼** — `pdf.html`의 해당 섹션 앵커로 연결되는 CTA
5. **자주 묻는 질문 4~5개** — 그 키워드에 특화된 질문. `pdf.html`의 기존 FAQ와 겹치지 않게 새로 작성.
6. **관련 페이지 링크** — 다른 두 신규 페이지 + `pdf.html` + `guide.html` 상호 링크

기존 `guide.html`/`pdf.html`과 동일하게 `container`, `info-section`, `tool-nav`, `subtitle` 등 `css/style.css`의 기존 클래스를 재사용하고, 새 CSS는 추가하지 않는다.

## SEO 메타데이터 & 구조화 데이터

기존 페이지들과 동일한 패턴(`title`/`meta description`/`canonical`/`og:type`/`og:title`/`og:description`/`og:url`/`og:locale`)을 따른다.

- 구조화 데이터는 **HowTo**(단계별 변환 방법) + **FAQPage**(자주 묻는 질문) 두 개를 함께 삽입한다. HowTo는 현재 사이트에 없는 새로운 rich-snippet 기회이며, "~하는 방법" 콘텐츠에 가장 적합한 타입이다.
- 제목(안):
  - `pdf-to-word.html`: "PDF를 워드(Word)로 변환하는 방법 - 무료, 온라인, 설치 없이"
  - `pdf-to-ppt.html`: "PDF를 파워포인트(PPT)로 변환하는 방법 - 무료, 온라인"
  - `photos-to-pdf.html`: "여러 장 사진을 하나의 PDF로 합치는 방법 - 무료"

## 내부 링크 연결

- `pdf.html`의 "PDF → 문서 변환" 섹션(`<h2>`) 근처에 "PDF→Word 자세히 보기" / "PDF→PPT 자세히 보기" 링크를 추가한다.
- `pdf.html`의 "이미지 → PDF" 섹션 근처에 "여러 장 사진 합치는 법 자세히 보기" 링크를 추가한다.
- `guide.html`의 관련 문단(2번 섹션: "여러 장의 이미지를 PDF로 합쳐야 할 때")에도 신규 페이지 링크를 추가한다.
- `sitemap.xml`에 3개 URL을 추가한다.

## 에러 처리

해당 없음 — 순수 정적 콘텐츠 페이지로, 실패할 수 있는 로직이 없다.

## 테스트 방침

- 빌드 도구가 없는 순수 HTML이라 자동화 테스트 대상이 아니다.
- 수동 확인: (a) 각 페이지의 CTA 클릭 시 `pdf.html`의 정확한 섹션으로 스크롤되는지, (b) 신규 페이지 간 상호 링크 및 기존 페이지에서의 진입 링크가 모두 정상 동작하는지, (c) HowTo/FAQPage JSON-LD가 문법 오류 없이 파싱되는지(브라우저 콘솔 또는 Google 리치 결과 테스트로 확인).

## 성공 기준

- 신규 페이지 3개가 각각 실제 콘텐츠(시나리오, 3단계 안내, 한계 고지, FAQ)를 갖추고 배포되어 있다.
- 각 페이지에서 `pdf.html`의 올바른 섹션으로 딥링크가 동작한다.
- 기존 페이지(`pdf.html`, `guide.html`)에서 신규 페이지로의 내부 링크가 추가되어 있다.
- `sitemap.xml`에 3개 URL이 반영되어 있다.
- 기존 기능(각 도구의 실제 처리 로직)에 회귀가 없다 — JS를 건드리지 않았으므로 자동으로 만족된다.
