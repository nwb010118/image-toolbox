# 압축 실측 벤치마크 페이지 설계 문서

- 작성일: 2026-09-09
- 상태: 승인됨 (구현 계획 단계로 진행)

## 배경 및 목표

AdSense 반려 대응 5단계 계획의 3단계. 외부 진단이 "가장 차별화되는 포인트"로 꼽은 것이 "직접 테스트한 압축률/화질 비교 데이터"다 — 막연한 설명이 아니라 실제로 도구를 돌려서 얻은 숫자를 근거로 한 콘텐츠. 이 단계는 압축 기능만 다룬다(업스케일링은 다음 라운드).

브레인스토밍 단계에서 실제로 배포된 `index.html`을 브라우저로 직접 조작해 실측을 완료했다. 아래 "실측 결과"는 가상의 예시가 아니라 이번 세션에서 실제로 측정한 값이다.

## 범위

`benchmark.html` 1개 신규 페이지를 저장소 루트에 추가한다. 새 변환 로직은 만들지 않는다 — 실측은 이미 완료됐고, 이 페이지는 그 결과를 정리해서 보여주는 콘텐츠 페이지다.

## 목표가 아닌 것 (Out of Scope)

- 업스케일링(AI 화질 개선) 비교 데이터 — 다음 라운드.
- 사용자가 실시간으로 자기 사진을 올려 비교해보는 인터랙티브 벤치마크 도구 — 이번엔 정적 결과 페이지만. (향후 아이디어로 남겨둘 수는 있음)
- 압축 전/후 이미지를 실제로 화면에 나란히 보여주는 비주얼 비교 — 브라우저 자동화로 압축 결과 파일을 로컬로 내려받는 것이 샌드박스 제약으로 불가능했음(다운로드가 인터셉트됨). 수치 데이터와 서술적 설명으로 대체한다.

## 실측 방법론 (페이지에 그대로 서술할 내용)

- 저작권 문제가 없고 재현 가능하도록, 실제 사진 대신 **브라우저 canvas로 직접 그린 합성 테스트 이미지 2종**을 사용했다:
  - "사진형": 그라디언트+방사형 하이라이트+노이즈로 만든, 실제 사진과 비슷한 고디테일 이미지 (1200×800)
  - "그래픽형": 단색 블록+얇은 선으로 만든 UI 스크린샷 스타일 이미지 (1200×800)
- 실제 배포된 `index.html`의 압축 기능을 그대로 사용해(같은 Canvas API 재인코딩 로직) 품질 100/80/60/40/20%에서 JPG·WebP로 각각 변환하고, PNG는 품질과 무관하게 크기가 변하는지도 실측했다.
- 결과 파일 크기는 화면에 표시되는 반올림된 문구가 아니라, 실제 생성된 Blob의 정확한 바이트 수를 측정했다.

## 실측 결과 (페이지에 표로 담을 데이터)

### 사진형 이미지 (원본 PNG 1,808,456 바이트 ≈ 1.72 MB)

| 품질 | JPG | WebP |
|---|---|---|
| 100% | 787,571 B (769 KB) | 1,019,768 B (996 KB) |
| 80% | 115,393 B (113 KB) | 123,720 B (121 KB) |
| 60% | 54,859 B (53.6 KB) | 39,472 B (38.5 KB) |
| 40% | 29,345 B (28.7 KB) | 14,514 B (14.2 KB) |
| 20% | 11,638 B (11.4 KB) | 7,114 B (6.9 KB) |

PNG는 100/50/10% 전부 1,808,456 바이트로 **완전히 동일**(원본 그대로) — 이론이 아니라 실측으로 재확인됨.

핵심 관찰: 80% 품질에서 JPG는 원본 대비 **93.6% 용량 절감**. 100%에서 60%로 낮춰도 파일 크기는 급격히 줄지만(787KB→55KB), 실무적으로는 80% 부근이 합리적인 시작점.

### 그래픽형 이미지 (원본 PNG 22,791 바이트 ≈ 22.3 KB)

| 품질 | JPG | WebP |
|---|---|---|
| 100% | 35,171 B (34.3 KB) | 6,010 B (5.9 KB) |
| 80% | 18,709 B (18.3 KB) | 3,702 B (3.6 KB) |
| 60% | 16,544 B (16.2 KB) | 3,670 B (3.6 KB) |
| 40% | 14,908 B (14.6 KB) | 3,662 B (3.6 KB) |
| 20% | 13,105 B (12.8 KB) | 3,972 B (3.9 KB) |

PNG는 100/50% 전부 22,791 바이트로 동일.

핵심 관찰(가장 차별화된 발견): **JPG 100% 품질이 원본 PNG(22.3KB)보다 오히려 더 큰 34.3KB로 나온다.** 단색·선명한 경계가 많은 그래픽 콘텐츠에는 JPG 압축 방식 자체가 안 맞기 때문이다. 반면 WebP는 100% 품질에서도 원본보다 73.6% 작은 5.9KB — 그래픽 이미지에는 PNG보다 WebP가 낫다는 것을 실측으로 보여준다.

## 페이지 콘텐츠 구조

`about.html`/`contact.html`과 동일하게 `container`/`info-section`/`tool-nav`/`btn`/`site-footer` 클래스를 재사용한다.

1. **H1 + 소개** — "실제로 압축해봤습니다"류의 도입, 이 페이지가 막연한 설명이 아니라 실측 결과임을 명시
2. **테스트 방법** — 위 방법론 서술(합성 이미지 사용 이유, 실제 도구로 직접 테스트, 정확한 바이트 단위 측정)
3. **사진형 이미지 결과** — 표 + 핵심 관찰 1~2문장
4. **그래픽형 이미지 결과** — 표 + "JPG가 PNG보다 커지는 역전 현상" 핵심 관찰
5. **실측 기반 권장 설정** — 사진: JPG/WebP 80% 부근이 합리적, 그래픽/스크린샷: WebP 권장(단, WebP는 완전 무손실은 아니므로 픽셀 단위 정확도가 중요하면 PNG 유지)이라고 과장 없이 조건부로 서술
6. **직접 해보기** — `index.html`로 이동하는 CTA 링크

## SEO 메타데이터 & 구조화 데이터

기존 페이지들과 동일한 패턴을 따른다. `og:type`은 `guide.html`/`about.html`과 동일하게 `article`. 구조화 데이터는 실측 수치를 표로 담은 콘텐츠 특성상 `Article` 타입을 사용한다(현재 사이트에 없는 타입).

## 내부 링크 연결

- `index.html`의 "압축은 어떻게 동작하나요" 섹션 근처에 "실제 압축률 비교 결과 보기" 링크 추가.
- 사이트 전체 10개 페이지 footer에 있는 About/문의 링크 패턴과 동일하게, `benchmark.html`도 모든 페이지 footer에 추가하지는 않는다 — footer는 신뢰 페이지(About/문의/개인정보) 전용으로 유지하고, `benchmark.html`은 `index.html`에서의 콘텐츠 내 링크와 `guide.html`에서의 관련 링크로 충분히 연결한다(footer 과밀화 방지).
- `guide.html`의 "1. 사진 용량을 줄여야 할 때" 섹션에 링크 추가.
- `sitemap.xml`에 1개 URL 추가.

## 에러 처리

해당 없음 — 순수 정적 콘텐츠 페이지.

## 테스트 방침

- 기존 `tests/seoPagesIntegrity.test.js`에 `benchmark.html`의 head 태그, `index.html`/`guide.html`에서의 링크, `sitemap.xml` 반영 여부를 검증하는 항목을 추가한다.
- 표에 담긴 수치 자체는 이미 이번 세션에서 실측 완료된 값이므로 별도 자동 재검증은 하지 않는다(정적 텍스트).

## 성공 기준

- `benchmark.html`이 실제 측정된 수치를 담은 표 2개와 방법론 설명, 권장 설정을 갖추고 배포되어 있다.
- `index.html`, `guide.html`에서 `benchmark.html`로의 링크가 정상 동작한다.
- `sitemap.xml`에 URL이 반영되어 있다.
